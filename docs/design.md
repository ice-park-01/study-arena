## 1. 의도

HW6은 "지금까지 배운 DevOps, TDD, Agent가 모두 들어간 제품 수준 결과물"을 학생이 자유 주제로 개인 개발하는 과제다. 이 프로젝트는 그 과제의 **참조 구현**이다. 용도는 둘이다.

- 튜토리얼 도입부에서 "이 정도가 제품 수준"이라는 기준점으로 보여준다.
- 기능 하나를 테스트 작성부터 배포까지 실시간으로 시연하는 바탕 저장소로 쓴다.

제품 자체는 **시험 대비 학습 도우미 + 친구와의 공부 시간 대결**이다. 강의자료를 올리면 문제를 내 주고, 친구를 초대해 공부 시간을 겨룬다(열품타와 비슷한 방식).

## 2. 목표, 비목표, 실패 조건

**목표**

- 학생 노트북(Windows 포함)에서 `docker compose up` 한 번으로 실행된다.

**실패 조건** (동작하더라도 실패로 본다)

- 커밋 이력에서 구현이 테스트보다 먼저 나온다.

## 3. 제약

- 수업은 2026-11-26이다. 필수 범위가 먼저 끝나야 하고, 가산점 범위는 시간이 남을 때만 한다.
- 개발 Mac에는 Docker가 설치돼 있지 않다. Dockerfile과 Compose 파일은 작성하되, 이 환경에서는 컨테이너 실행을 검증할 수 없다. 검증은 Docker가 있는 기기 또는 GitHub Actions에서 한다.
- 작업 폴더가 네트워크 드라이브다. SQLite와 git이 느리거나 잠금 오류를 낼 수 있다. 문제가 생기면 로컬 디스크에서 개발하고 결과만 이 폴더로 옮긴다.
- LLM은 ChatKHU(OpenAI 호환 게이트웨이, `https://factchat-cloud.mindlogic.ai/v1/gateway`, 환경 변수 `FACTCHAT_API_KEY`)를 쓴다. 강의자료에는 Codex 연결용 Responses API 설정만 있어서, 일반 코드에서의 호출 형식·모델 이름·호출 한도는 실제 키로 확인해야 한다.
- 학생들이 익숙한 기술을 쓴다: Python, FastAPI, GitHub Actions, Docker Hub, Self-hosted Runner (HW2, HW3과 동일).

## 4. 검토한 방식

| 방식 | 내용 | 장단점 |
|---|---|---|
| **A. 단일 FastAPI + SQLite + 작업자 컨테이너 (채택)** | 서버가 화면까지 그려 주고, 같은 이미지를 명령만 바꿔 작업자로도 실행 | 설치할 것이 적고 HW2·HW3과 구조가 같아 학생이 따라오기 쉽다. 동시 사용자가 많으면 SQLite가 한계다. |
| B. FastAPI + PostgreSQL + Redis 작업 큐 | 실무에 가까운 구성 | 컨테이너가 4개로 늘어 학생 노트북에 무겁고, 시연에서 설명할 것이 많아진다. |
| C. React 화면 + API 서버 분리 | 화면이 매끄럽다 | 빌드 단계와 검토할 코드가 늘고, 과제의 초점(TDD, 배포)에서 벗어난다. |

A를 채택한다. 스터디 그룹은 수 명 규모라 SQLite로 충분하고, 시연 때 구조 설명에 쓸 시간이 가장 적다. (작성자의 판단이며 사용자가 고른 것은 아니다.)

## 5. 기능

### 필수 범위

1. **계정**: 닉네임과 비밀번호로 가입·로그인한다. 비밀번호는 해시로 저장한다.
2. **자료 업로드**: pptx, pdf, txt를 올리면 슬라이드·페이지 단위 조각으로 나눠 저장한다. 처리는 작업자가 백그라운드로 한다.
3. **문제 출제**: 조각을 LLM에 보내 객관식과 주관식(단답·짧은 서술) 문제를 만든다. 검증을 통과한 문제만 저장한다(6절). 시연 자료는 이 수업의 강의자료(pptx)를 쓴다. 강의자료 파일은 저장소에 넣지 않는다(교수님 자료이므로 `.gitignore`로 제외).
4. **풀이와 채점**: 문제를 풀면 즉시 채점하고 근거 조각을 보여준다. 틀린 문제는 오답 목록에 쌓인다.
5. **공부 타이머**: "공부 시작"을 누르면 시간이 쌓인다. 화면이 보이는 동안 브라우저가 30초마다 신호를 보내고, 서버가 이를 공부 세션으로 합친다(7절).
6. **스터디 그룹과 대결**: 그룹을 만들면 초대 코드가 나온다. 코드로 가입한 친구들의 오늘·이번 주 공부 시간 순위와 "지금 공부 중" 표시를 보여준다.

올린 자료와 만들어진 문제는 올린 사람만 본다. 그룹은 공부 시간 순위만 공유한다. (작성자의 판단)

### 만드는 순서와 줄이는 순서

시연에 꼭 필요한 것부터 만든다.

1. 문제 검증·채점 로직과 CI 테스트 게이트 (실시간 시연의 바탕)
2. 계정, txt·pptx 업로드, LLM 출제와 빈칸 문제 대체
3. 풀이 화면과 오답 목록
4. 공부 타이머
5. 스터디 그룹과 순위
6. 배포 파이프라인, 상태 확인

시간이 모자라면 다음 순서로 줄인다: pdf 업로드 → 작업자 컨테이너 분리(업로드 요청 안에서 바로 처리) → "지금 공부 중" 표시 → 이번 주 순위(오늘 순위만 남김).

### 가산점 범위 (시간이 남을 때)

- 그룹 안에서 자료와 문제 공유

- 복습 간격: 맞히면 다음 출제 간격이 늘고, 틀리면 처음으로 돌아간다.
- LLM 주간 코멘트: 그룹의 한 주 기록을 요약해 한 줄 응원을 쓴다.

## 6. LLM 계약

LLM 응답은 매번 달라서 그대로 테스트할 수 없다. 응답을 다루는 코드를 테스트한다.

- 문제마다 근거 조각 번호가 있어야 하고, 그 번호는 실제로 보낸 조각 중 하나여야 한다.
- 정답 문구의 핵심어가 근거 조각 본문에 있어야 한다.
- 객관식: 보기는 4개이고 서로 달라야 하며, 정답은 그중 하나여야 한다.
- 주관식: 모범답안과 핵심어 2~5개가 있어야 하고, 핵심어는 모두 근거 조각 본문에 있어야 한다.
- 주관식 채점: LLM에 문제·모범답안·근거 조각·학생 답을 보내 `정답 여부`와 `한 줄 피드백`을 받는다. 정답 여부가 참/거짓이 아니면 버리고 핵심어 채점으로 대체한다.
- 핵심어 채점(대체 동작): 학생 답에 핵심어의 60% 이상이 들어 있으면 정답이다. 띄어쓰기와 대소문자는 무시한다. 채점 결과에는 LLM 채점인지 핵심어 채점인지 표시한다.
- 위를 어긴 문제는 저장하지 않고 버린 개수를 기록한다.
- 응답이 JSON이 아니면 한 번 재시도한다.
- 키가 없거나 호출이 실패하면 **빈칸 문제**(조각에서 핵심어를 가린 문제)를 규칙으로 만들어 대체한다. 서비스는 멈추지 않는다.
- 호출 횟수, 실패 횟수, 버린 문제 수를 기록해 화면에서 볼 수 있게 한다.

## 7. 공부 시간 규칙

조작을 막기 위해 시간은 서버 시계로만 계산한다.

- 신호 하나는 최대 30초만 인정한다. 브라우저가 보낸 시각은 믿지 않는다.
- 마지막 신호 뒤 90초 동안 신호가 없으면 세션을 끝낸다.
- 화면이 가려지면 브라우저가 신호를 멈춘다.
- 한 사용자가 여러 탭을 열어도 시간은 한 번만 쌓인다.
- 순위의 "오늘"과 "이번 주"는 한국 시간 기준이고, 자정을 넘는 세션은 날짜별로 나눠 집계한다.

## 8. 구조

```
study-arena/

    main.py        FastAPI 진입점, 화면과 API
    auth.py        가입, 로그인, 세션
    ingest.py      파일 → 조각
```

- 시계와 LLM은 인자로 주입해 테스트에서 바꿔 끼운다.

## 9. DevOps

- **테스트 게이트**: CI 첫 단계에서 `pytest`를 돌리고, 실패하면 빌드와 배포가 실행되지 않는다.
- **자동 배포**: HW3과 같은 방식(Docker Hub + Self-hosted Runner)이다.
- **실행 방법 두 가지**: `compose.yml`은 로컬에서 이미지를 직접 빌드한다(Docker Hub 계정 없이 실행 가능). 배포 워크플로만 Docker Hub의 이미지를 받아 쓴다.
- **비밀값**: `FACTCHAT_API_KEY`는 GitHub Secrets에 두고 배포 때 컨테이너 환경 변수로 넘긴다.
- **데이터 보존**: SQLite 파일과 업로드 자료는 볼륨에 둔다. 재배포 뒤에도 계정과 기록이 남는다.
- **상태 확인**: `/health`가 DB와 작업자 상태를 알려 주고, 배포 단계가 이것으로 성공을 판단한다.
- **가산점**: 상태 확인에 실패하면 이전 이미지로 되돌린다.

## 10. 개발 방식

- 기능마다 실패하는 테스트를 먼저 커밋하고, 그다음 구현을 커밋한다. 커밋 이력이 과제의 TDD 근거 예시가 된다.
- `AGENTS.md`에 이 규칙과 "테스트에서 외부 호출 금지", "키를 코드에 쓰지 않기"를 적는다.
- 시연용으로 **기능 하나를 일부러 남겨 둔다**: "근거 조각이 없는 문제는 버린다"의 테스트와 구현은 `demo-start` 브랜치에 넣지 않고, 완성본은 `main`에 둔다. 튜토리얼에서 이 기능을 실시간으로 만든다.

## 13. 사용자 확인이 필요한 것

- GitHub 저장소를 새로 만들지, 만든다면 공개 여부 (CI와 배포 검증에 필요)
- ChatKHU 실제 호출 검증에 쓸 키 (채팅에 붙여넣지 말고 `.env` 파일에 직접 저장)
- Docker가 있는 검증 기기
- Docker Hub 계정 (CI가 이미지를 올릴 곳, Secrets 등록은 사용자가 직접)
- 수업 당일 배포를 실제로 실행할지와 어느 기기에서 할지. 실제로 한다면 발표 기기에 Docker와 Self-hosted Runner가 미리 준비돼 있어야 한다. 기본안은 "발표 기기에서 실제 push, 미리 녹화한 실행 화면을 백업으로 준비"다.
